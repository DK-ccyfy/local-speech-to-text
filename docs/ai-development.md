# AI 辅助开发记录（ai-development.md）

> 本项目在 AI 编程工具辅助下完成开发。本文档记录 AI 承担的任务、人工做出的关键决策、
> 遇到的问题与解决方式、对 AI 产出的验证方法，以及后续优化方向。
> （提交前可按考核要求补充/替换为实际使用的 OpenCode 会话导出证据。）

## 1. 开发方式概述

整体流程：**人工提出需求与验收标准 → AI 产出实现计划 → 人工确认 → AI 编码/测试 → 人工验证关键节点**。
开发按阶段推进，每个阶段以可运行的产物收口（先跑通骨架，再补功能与测试，最后真实模型验证与文档）。

## 2. 阶段一：需求理解与技术设计

**AI 承担的任务：**
- 通读考核题目，输出结构化需求拆解（功能矩阵、异常处理映射表、假设与边界条件，见 `docs/requirements.md`）；
- 调研并对比本地 ASR 候选模型（faster-whisper / openai-whisper / Vosk / FunASR / sherpa-onnx），给出选型建议表；
- 设计系统架构：接口契约、模块划分（FastAPI + ASRService 抽象 + PyAV 解码 + 原生前端）、可测试性方案（依赖注入 Mock）；
- 制定实施步骤与里程碑。

**人工决策：**
- 确认采用 **faster-whisper small / int8 / CPU**（准确率与速度平衡；低配可切 base）；
- 确认实现**实时识别加分项**，且采用「每 3 秒整段重识别」方案而非引入流式模型（实现简单、无切词错误、复用同一接口）；
- 确认不做 git 仓库、直接以当前目录为项目根（保证统一启动命令可用）。

## 3. 阶段二：功能开发与集成

**AI 承担的任务：**
- 后端：FastAPI 应用（/health、/api/transcribe、静态页）、PyAV 统一音频解码（WAV/WebM/MP3 → 16k mono float32）、WhisperASRService（后台预热 + 懒加载 + 状态机 + 超时保护）、异常→HTTP 映射；
- 前端：原生 HTML/CSS/JS 单页（录音状态机、AudioWorklet 采集 PCM、前端 WAV 编码、60 秒上限自动停止、实时预览、上传预检、复制、错误文案与重试）；
- 测试：41 个 Mock 用例（API 契约、非法参数、损坏文件、超限、模型异常、加载策略、音频解码、前端冒烟）+ 5 个真实模型用例（标记 `realmodel`）；
- 样本音频生成脚本（macOS `say` TTS + `afconvert` 转 16kHz WAV）、模型预下载脚本、README 与三份文档。

**人工决策：**
- 录音格式定为「浏览器直接生成 WAV」（而非上传 MediaRecorder 的 WebM）：时长精确、60s 判定精确、实时预览天然可用；后端仍支持 WebM 兼容上传；
- `processing_seconds` 口径：解码 + 推理，排除模型加载时间（与题目要求一致）。

## 4. 阶段三：测试与问题修复（实际案例）

开发过程出现过的真实问题及处理：

| # | 问题 | 定位与修复 |
|---|---|---|
| 1 | 首轮 Mock 测试 6 个失败：断言写错（1.5s 音频按 15000 采样断言，实际 24000）；空 language 走 FastAPI 422 而非自定义 400；TestClient 默认重抛服务端异常导致 500 用例失败 | 逐一修正断言与预期：空串归入 4xx 断言、500 用例改 `raise_server_exceptions=False`；同时暴露出「Mock 直抛 RuntimeError 由兜底处理器统一返回『服务器内部错误』」的正确行为，据此补了 WhisperASRService 桩模型单测（验证内层 500 包装） |
| 2 | 截断 WAV 测试失败：PyAV/FFmpeg 对截断文件容错解码有效部分，不抛异常 | 确认这是可接受的工程取舍（能解码就返回可识别内容），删除该用例并在 requirements.md/test-report.md 说明；完全损坏的文件仍 400 |
| 3 | 模型直连 HuggingFace 超时（ConnectTimeout）| 使用 `HF_ENDPOINT=https://hf-mirror.com` 镜像下载成功；镜像又触发 Xet 存储 401，再设 `HF_HUB_DISABLE_XET=1` 改走普通 HTTP 下载；两个环境变量都写入 README |
| 4 | Chrome 只调度连接到 destination 的音频节点，Worklet 若不连 destination 会收不到数据；直连又会回放麦克风产生啸叫 | Worklet → 增益 0 节点 → destination：保持数据流且静音 |
| 5 | 识别推理若在事件循环内执行会阻塞 /health | 解码与推理均经 `run_in_threadpool` 执行 |
| 6 | 浏览器实测时服务端模型长时间停在 loading：已缓存模型仍尝试联网校验版本，直连 HF 超时拖住加载线程 | 重构加载策略为「离线优先」：先 `local_files_only=True` 用缓存秒级加载，未命中才联网下载；补 3 个单测锁定该行为，并用 `HF_HUB_OFFLINE=1` 实机验证断网可用 |

**如何确认 AI 生成代码满足需求：**
- 每阶段用 `python -m pytest -q` 回归（37 用例全绿）；
- 真实模型套件 `-m realmodel` 验证中英文识别质量（关键词重合度断言 + 人工目视比对参考文本）；
- 浏览器手动验证清单（见 test-report.md）：录音/上传/权限拒绝/超限/无语音等路径逐项确认。

## 5. AI 承担任务小结

| 任务 | AI | 人工 |
|---|---|---|
| 需求拆解、方案设计、选型对比 | 产出与建议 | 审阅、拍板 |
| 后端/前端/测试代码 | 编写 | 审阅关键路径、验收 |
| 异常处理矩阵 | 全量实现 | 逐项验证 |
| 样本音频 | 脚本生成 | 确认内容无敏感信息 |
| 文档 | 初稿 | 核对口径与提交要求 |

## 6. 后续优化方向（若继续开发）

1. **流式实时识别**：WebSocket + sherpa-onnx/Whisper 流式方案，降低预览延迟与重复计算；
2. **模型规格自适应**：按机器核数/内存自动选 base/small，或提供页面内切换；
3. **识别历史**：本地 SQLite 存储（题目范围外，但演示友好）；
4. **并发与队列**：多请求排队与背压（当前单用户假设）；
5. **播放器**：结果区附带原始音频回放，便于比对。
